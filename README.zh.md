# 🧭 dsh-session-navigator

> DeepSeek Harness 跨会话深层直达、多窗口导航，以及把会话复制成可粘贴的 `@` 引用  
> 增强**左上角官方「搜索会话」**（不是 Codex Timeline 搜索），让聊天里的 session id 能在新窗口打开指定会话 / 轮次，并在侧栏会话 `⋯` 菜单提供「复制会话 ID」和「复制会话引用」。

---

## 解决的痛点

1. 官方侧栏搜索只匹配标题和工作区名，输入 `56c6db` 这种 Session ID 会显示「无匹配会话」；
2. 点开历史会话会冲掉当前窗口；
3. 长会话里要自己数「第几轮」；
4. `@` 引用另一个会话时必须在输入框里搜标题，侧栏 `⋯` 菜单没有复制入口；也拿不到稳定的 session ID。

---

## 核心行为

### 1. 只增强左上角官方搜索框

目标输入框的文案是 **「搜索会话…」** / **Search sessions...**，在会话列表上方。

- **不**劫持右侧 Codex Timeline 的历史搜索；
- **不**在对话区再插一块「精准 ID / 内容匹配」浮层。

做法：输入时立刻用内存会话列表匹配 ID（不等全文检索），在官方结果区顶部显示「会话标题 + ↗」。点标题在当前窗口打开；点 **↗** 新窗口打开。

侧栏会话列表的**普通点击**不会弹窗，交给官方在当前窗口切换。只有聊天里的会话芯片、搜索结果 **↗**、以及 **Cmd/Ctrl + 点击** 才会开新窗口。

### 1.1 每个 origin 只能开 3 个标签（0.3.6 定论）

> **勘误**：0.3.5 曾把这个现象归因于「`localhost` 被外部应用劫持」。**那是错的。**
> 当时 `localhost` 上有 10 个标签、`127.0.0.1` 上只有 1 个，我把标签数量差异误读成了 host 差异。
> 真正的变量是**同一个 origin 上已经开了几个 DSH 标签**。

**真正的机制：连接池被 DSH 自己的长连接占满。**

DSH 每个标签要维持约 4 条长连接（HMR 事件流 / 连接流 / 会话控制流 / 日志流）。
Chrome 对单个 origin 的 HTTP/1.1 并发连接上限是 **6**。于是：

| 同一 origin 上已有的 DSH 标签 | 再开一个标签的结果 |
|---|---|
| 0 – 2 个 | 正常加载 |
| 第 3 个 | 正常加载（实测 3 个标签 ≈ 13 条连接） |
| 第 4 个 | **一条连接都拿不到，永远停在 `about:blank`** |

空 origin 下逐个开标签的实测记录：第 1 个 24 条连接、第 2 个 27、第 3 个 28，第 4 个 ——
连接数纹丝不动，标签一直是空白。

**最坑的地方是 Chrome 不报错**：标签建出来了、地址栏也填好了，但导航从未提交，文档停在
初始的 `about:blank`。用户看到的就是「点开是个空白页」，而且刷新也没用 —— 因为池子还是满的。

这也顺带解释了另外两个怪现象：

- **页面里的 `fetch` / `XHR` 永久挂起**（不是报错、不是 401，就是永远 pending）。
  宿主路由本身没问题，同一条请求用 `curl` 打是 2ms 返回 —— 是浏览器拿不到连接；
- **点了没反应、也不 fallback**：0.3.2–0.3.4 开新标签要先 `fetch` 宿主路由，而那个 fetch
  永不 settle，`await` 卡死、`.catch` 也不触发，点击被静静吞掉。

不只是「新标签」受影响：池子满的时候，**已开标签里的模型目录请求也会挂起**，表现就是输入框
一直「正在加载模型…」、发不出消息。所以「标签太多」是会互相拖垮的。

#### 0.3.6 的对策

1. **默认点击 = 在当前窗口切换。** 当前窗口的会话列表早已加载好，切换是瞬时的，而且不新增
   任何连接 —— 唯一不受 3 标签上限影响的路径。会弹一条「已切换会话 · 按住 ⌘ 点击可开新标签」；
2. **⌘/Ctrl + 点击（以及搜索结果的 ↗）= 开新标签**，回到原生 `window.open`；
3. **开完新标签必须验证。** 连接耗尽时没有任何错误可捕获，所以 0.3.6 会探：新标签若在 8 秒内
   一直停在 `about:blank`，就判定失败 —— **关掉那个空白标签**，退回到当前窗口切换，并弹提示
   说明原因。宁可少一个标签，也不留一个看不懂的空白页；
4. 容量够时新标签正常加载，探针不会误杀（有容量 / 无容量两条路径都实测过）。

**实用建议：同一个地址（origin）上最多留 3 个 DSH 标签。** 第 4 个一定是空白页。
`dsh web` 启动时打印的 `http://127.0.0.1:3080/...` 就是推荐地址（`navUrl()` 也会把
`localhost` 归一成 `127.0.0.1`，纯粹为了统一，与上面的连接上限无关）。

### 1.2 跨会话直达为什么以前要等几分钟（0.3.2 起）

官方没有页面路由：新窗口启动时只从 `localStorage` 的 `dsh.sessions.current` 恢复上次选中的会话，完全忽略 URL 上的 `?session=`。所以直达必须由插件在窗口内抢一次选择。

- 不再预写官方共享的 `dsh.sessions.current`（那会把原窗口的当前会话一起改掉）。新标签只认自己 URL 上的 `?session=`；
- 会话很多时 `session.list` 可能**几十秒到几分钟**才到（本机 430+ 会话实测有一次约 6 分钟）。旧实现只重试 8 秒就放弃，于是窗口停在别人/空白上 —— 这就是「点链接开了个空白窗口」的根因。0.3.2 改成按**预算**等待（默认 15 分钟）而不是按次数，列表一到就立刻兑现；
- 列表就绪后有 20 秒「结算窗口」持续抢回选择，压过官方自己的启动导航；之后再出现别的 current 就判定为用户所选，立即退位，绝不和用户抢；
- 等待期间页面顶部显示「正在打开目标会话…」，避免那段空窗期被误解成坏掉。

### 1.2.1 秒开：借官方增量通道单条注入（0.3.4 起）

1.2 的「等列表 + 抢选择」是绕路。真正的拦路石只有一行守卫 —— 官方
`sessions.select()` 拒绝任何「还不在已加载会话列表里」的 id：

~~~
sessions.select: unknown session <id>
~~~

而那份列表要对全库每个冷会话逐个算投影。本机 429 个会话实测要几分钟，
**跟你想看的那一个会话毫无关系**；会话内容本身打开时只拉它自己的尾巴一页。

官方自己推送「新增了一个会话」走的是 `sessions.handleSessionAdded(summary)`，
它经 mergeSummary → applyMutation 的 upsert 分支直接前插，不校验列表。
0.3.4 就用这条官方增量通道把目标单独喂进去：

1. 新宿主路由 `GET /dsh-session-navigator/session-summary?id=<session-id>`
   读一个投影缓存文件（`~/.dsh/storages/session_projcache/sessions/<id>.json`），
   取出 `title` / `sessionListMetadata` / `identity.cwd`，拼成一条列表 summary。
   单次约 2ms，路径穿越由严格的 session id 形状校验挡掉。
2. 客户端拿到后 `handleSessionAdded(summary)` 再 `open(id)`，守卫立刻放行，
   **不必等那份全量列表**。标题随 `projections` 一起带上，侧栏不会先显示裸 id。
3. `handleSessionAdded` 缺失或缓存没有这条记录时，静默回落到 1.2 的等列表路径 ——
   官方未来若改内部实现，深链只会变回「慢」，不会变成「坏」。

同时删掉了深链前对 `uiWorkspace.connectWorkspace()` 的调用：它在「该工作区里没有空白会话」
时会**直接创建一个新会话**，而列表未加载时 `sessions.ids` 是空数组，于是每次深链都白送
一个垃圾空白会话。内容区渲染并不需要它。

0.3.2 的等列表路径整体保留为兜底，`DEEP_LINK_MAX_WAIT_MS`（15 分钟）只在这条兜底路径上生效。

### 1.3 CPU

`enhanceDom` 自己会改 DOM。观察器在改写期间保持连接的话，每一轮改写都会触发下一轮，形成永不停止的重扫（大会话下表现为标签页持续占 CPU）。0.3.2 在改 DOM 前先 `disconnect()`，改完再接回。

### 2. 聊天里的会话直达

DSH Markdown 不会把 `/?session=` 相对链接渲染成可点 `<a>`。配套 Skill 要求把完整 session id 写在行内代码里；插件把它画成和官方 `@` 会话 mention 一样的芯片（气泡图标 + 标题），id 和轮次放在 tooltip。Skill 那行重复的「查看会话：标题」会被藏掉。点击后新窗口打开并滚动到 `[data-chat-turn]`。

同页的 http(s) 会话链接会改写为当前源相对地址，避免 Better Sidebar 当成外部网页拦走。

### 3. 复制会话 ID / 复制会话引用 / 置顶

侧栏会话行的 `⋯` 菜单在官方「重命名 / 分叉 / 归档」上方增加三项：

1. **置顶会话 / 取消置顶**：钉到侧栏列表顶部的「置顶」分组，原行左侧留一条色标。状态写在宿主 `$DSH_HOME/session-navigator/pins.json`，刷新、换浏览器都还在。
2. **复制会话 ID**：纯 `session-xxxxxxxx-…`，给搜索、磁盘路径、日志对照。
3. **复制会话引用**：官方规范 mention，粘贴进输入框会变成和 `@` 点选一样的会话 chip（气泡图标 + 标题）。

```text
@[会话标题](dsh-session:<base64url>)
```

官方 `⋯` 菜单是 portal，菜单项不在 `role="menu"` 的直接子节点里。0.4.2 把克隆项插进 viewport，并在菜单开着时自愈 React 重渲染擦除。即便没变成 chip，发送时宿主仍会按 `dsh-session:` URI 注入被引用会话的快照。一条消息最多 3 个不同会话，这是官方 `dsh-session-reference` 的硬上限。

## 安装

开发机：

```bash
pnpm --dir ~/.dsh/profiles/web add link:~/Documents/dshspace/plugins/dsh-session-navigator
```

改完 host / client 后需要重启一次 `dsh web`（不要在对话里代劳杀进程）。

Skill：

```bash
ln -sfn "$HOME/Documents/dshspace/plugins/dsh-session-navigator/skill" "$HOME/.agents/skills/dsh-session-navigator"
```

## 0.4.1 · 换地址分流下线，标签容量问题在根上解决

「同一地址开到第 3–5 个标签就卡住」的真因是两个**每个标签各占一条**的常驻 SSE：
官方 `client-hmr` 的 `/plugins/events`，以及 badge 通知流 `/dsh-app-badge/events`。
浏览器对单个 host:port 只给约 6 条并发连接，`6 ÷ 2 = 3`。

两条都已解决（插件侧单例 + 关掉 dev-only 的 client-hmr），每个标签的常驻 HTTP 连接降到 **0**，
实测同地址连开 12 个标签全部正常加载。因此 0.4.0 引入的「自动挑另一个 loopback 地址」和
「换个地址打开」提示一并删除：

- 登录 cookie 按 `host:port` 签发，`127.0.0.1` 与 `localhost` 各自独立；
  被分流过去的那一边没有 cookie，打开就是 `dsh web authentication required` 的 401 页面。
- 容量不再紧张，分流的收益是 0，代价是一张看不懂的 401。

现在所有会话链接都只开**当前地址**，新标签打不开时退回当前窗口切换并说明原因。

### 关掉 client-hmr 到底损失了什么（2026-09-12 实测）

这件事一开始被低估了，记在这里免得下次再猜。

先看事实。热重载开着时，改 `dsh-app-badge/client.js` 后**不重启**，服务端返回的 bundle
在 4 秒内就带上了新代码，rev 从 `443564cd6a6de562-56` 变成 `634b448f2983`。
也就是说：**客户端插件（`client.js`）的改动，热重载确实能自动生效，不需要重启。** 关掉它，
这部分能力是真的丢了，改完必须重启 `dsh web`。

但有个边界要说清楚：热重载**只覆盖客户端半边**。宿主半边（`index.js` 的路由、`package.json`、
`cordis.patch.yml`）任何时候改动都要重启——这条在开关热重载之前就成立。
如果印象里「做插件一直都要重启」，多半是因为改宿主代码的次数不少。

所以这是一个**交换**，不是纯赚：

| | `/plugins/events` | 单地址可开标签 | 改 client.js 后 |
|---|---|---|---|
| 热重载开 | 每标签 1 条常驻 | 约 4–5 个 | 自动生效，不用重启 |
| 热重载关 | 0 条 | 12 个以上（实测） | 需要重启 `dsh web` |

两边争的是同一份资源：浏览器给单个 host:port 约 6 条并发连接。

切换方式（改一行 + 重启）：

```yaml
# ~/.dsh/profiles/web/cordis.patch.yml
- id: client-hmr
  disabled: true    # 改为 false 即恢复热重载，代价是标签上限降到 4–5
```

默认选「关」是因为这个插件的存在意义就是多开标签；要连续调客户端 UI 时再打开。
